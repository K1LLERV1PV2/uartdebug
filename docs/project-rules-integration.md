# Согласование правил репозитория и сайта

Сайт использует полный неизменённый источник `Sergey-Bulanov/UartDebug2` и отдельный адаптационный контракт. Правила коллеги описывают диалоговую работу с файлами, а сайт выполняет одно выбранное действие над браузерным проектом. Эти две модели требуют явного согласования полномочий и форматов.

Контракт находится в [avr-project-policy.js](../backend/avr-project-policy.js). Он задаёт общую таблицу стадий, единый текст политики для модели и сообщения предварительных проверок. Текст политики включается после четырёх полных исходных правил и начальных материалов базы. Исходные документы не переводятся, не сокращаются и не редактируются ради адаптации.

## Приоритеты

1. Возможности приложения, выбранная стадия, сохраняемые входы и ограничения инструментов задают верхнюю границу полномочий.
2. Внутри неё применяются явные требования и разрешённые указания выбранного пользовательского проекта.
3. Применяются канонические правила репозитория с их собственными приоритетами: дополнения 12 и 13 заменяют устаревшие предположения о разрешениях, версиях и именах; специальные применимые правила уточняют общие.
4. Шаблоны и примеры показывают структуру и приёмы. Их язык, имена, номера версий и значения не становятся требованиями нового проекта.

Достоверность аппаратных сведений рассматривается отдельно: применимая errata и уточнения исправляют затронутые положения даташита. DFP, извлечённый текст, модели, примеры и пользовательские предпочтения сохраняют указанные ограничения применимости и не подменяют первоисточник.

Если неразрешённое противоречие влияет на результат, агент сообщает конкретный недостающий выбор в пределах текущей стадии. Он не выбирает правило молча и не расширяет действие самостоятельно.

## Стадии и разрешения

| Действие сайта | Разрешённый результат | Обязательное сохранение |
| --- | --- | --- |
| Review specification / `analyze` | Замечания в спецификации; конкретная явно разрешённая правка требований | Требования и ответы пользователя без разрешения на их изменение; отсутствие новых C/YAML/описания |
| Generate / `generate` | C и скрытый YAML выбранного проекта | Спецификация и все существующие пользовательские области C побайтово |
| Describe / `describe` | Описание фактически переданного текущего C | Спецификация, C и YAML; выбранный язык и имя непустого существующего описания |

Нажатие кнопки уже разрешает указанную атомарную операцию, включая обновление переданных выходов и исправление собственных ошибок в них. Повторные файловые переговоры «что делаем дальше», «обычная или целостная правка», «использовать существующие или создать другие имена» не нужны внутри уже разрешённой области.

Для Review тип ответа всегда `clarify`, `project: null`, в том числе когда проверка успешно закончена и вопросов нет. Для других стадий `clarify` означает, что конкретный блокирующий вопрос не позволяет вернуть выходные файлы. Этот транспортный тип не следует путать с оценкой качества спецификации.

Пустой выбранный черновик можно проверить без заранее придуманного имени, версии или устройства. Недостающие сведения оформляются вопросами прямо в нём. Кнопка не разрешает создавать начальный текст требований от имени пользователя.

Спецификация запроса включает Markdown и явно выбранные значения `canvas.target`. Селекторы могут задавать отсутствующие в тексте модель и корпус; дублировать их в Markdown не требуется. Противоречивый или неоднозначный target в тексте блокирует генерацию даже при заполненных селекторах. Generate не дописывает выбор в основной текст.

## Найденные расхождения и их трактовка

| Исходное правило | Расхождение с сайтом | Единое правило адаптации |
| --- | --- | --- |
| `AGENTS.md`, переход к следующему шагу; дополнения 7 и 12 | Файловый диалог требует отдельных согласований перед изменениями | Выбранная кнопка задаёт точную область атомарного действия; уточнения нужны только для неизвестных решений или выхода за эту область |
| `Base_project_rules.md`, использование существующего комплекта | Начальная генерация предлагает выбор до работы с найденными C/YAML | Generate обновляет только переданные выходы выбранного проекта; не создаёт параллельный комплект и не переименовывает файлы |
| Правила выбора `Target_Projects` и локальных `AGENTS.md` | Браузерный проект не является выбранной папкой серверного зеркала | Используются только переданные документы выбранного проекта; одноимённая папка не выбирается автоматически |
| Постоянные `! ` и временные `!X`, `!+ … !-` | Разные виды указаний раньше не были явно разведены со стадиями | Постоянное указание сохраняется и действует лишь в допустимой области; временная пометка сама не даёт разрешения; примеры и цитаты не исполняются |
| Указания `//X` и возможность явной правки пользовательской области | Сайт всегда защищает пользовательские области C | Выполняются только указания внутри изменяемых областей ИИ; требующая ручной правки пользовательская область вызывает уточнение |
| Дополнение 5 и восстановление повреждённых маркеров | Валидатор не может безопасно подтвердить реконструкцию исходных пользовательских областей | Повреждённые или неоднозначные маркеры исправляет пользователь до генерации; агент не тратит повторы на заведомо недопустимый результат |
| Минимальная базовая программа и пустые аппаратные ресурсы | Generate должен реализовать функциональные требования сразу | Базовая программа задаёт структуру; области ИИ и ресурсы заполняются фактической реализацией, совместимые данные не стираются |
| Русские литералы в примерах спецификации, C и замечаний | Язык источника ошибочно становился языком пользовательского материала | Служебные ключи и новые машинные метаданные стабильны; содержательная часть, описание и новые подписи замечаний следуют языку материала |
| Дополнение 13: версии, варианты, копии | Выбор похожего файла по имени может смешать язык, версию и редакцию | Разрешение логического имени учитывает папку, расширение, вариант, версию проекта, версию файла, редакцию и номер копии; неоднозначность требует решения |
| Имя проекта в спецификации и отображаемое имя | Изменение отображаемого имени не означает переименования выходов | Идентичность берётся из спецификации; существующие допустимые имена сохраняются, подтверждённая пара C/YAML задаётся явно |
| Широкий поиск в Интернете по правилам базы | Инструмент сайта имеет два разрешённых корня официального HTML | Сначала общий локальный поиск по тому же запросу; затем конкретный пробел и до двух допустимых сетевых запросов. За пределами инструмента агент сообщает непроверенный пробел |

Документы выбранного проекта могут уточнять его требования в допустимой области. Они не предоставляют доступ к серверным файлам, соседним проектам, редактированию правил или произвольной сети. `Notes`, `Problems.md`, временные PDF-артефакты и невыбранные целевые проекты исключены из маршрута сайта.

## Язык и устойчивые идентификаторы

`canvas.locale` выбирает язык спецификации и новых замечаний. Региональные варианты используют базовый язык: `en-US` — английский, `ru-RU` — русский. Без явного языка он определяется по спецификации; пустой черновик по умолчанию использует английский. Непустое описание сохраняет собственный явно выбранный язык.

| Язык | Новое замечание | Новые подписи диалога |
| --- | --- | --- |
| Английский | `[AI.N] Question`, `Information`, `Error` | `User`, `AI` |
| Русский | `[ИИ.N] Вопрос`, `Информация`, `Ошибка` | `Пользователь`, `ИИ` |
| Другой | `[AI.N]` и переведённый тип | Переведённые подписи |

При Review смешанная подпись типа исправляется, но полный существующий идентификатор, ссылки и ответы сохраняются. Новые номера идут после наибольшего номера среди всех префиксов. Generate и Describe не изменяют даже старое написание замечаний в спецификации.

Для новых машинно распознаваемых метаданных используется стабильная форма `# Project <title>` и `Project version - Ver.X.Y`. Это не требует английского языка всего документа. Принятые локализованные формы существующих файлов не исправляются без разрешения. Новые метаданные C, метки его областей, ключи YAML и идентификаторы кода используют стабильные английские обозначения; поясняющие комментарии следуют языку материала. Существующие парные метки областей сохраняются при обновлении.

## Проверки и ограничения

Разбор спецификации, имён и версий вынесен в общий [avr-project-format.js](../backend/avr-project-format.js). Каталог сервера, валидатор выходов и импорт ZIP используют одни функции. Браузерная копия генерируется автоматически; CI проверяет её побайтовое совпадение. Примеры кода, замечания ИИ и ещё не применённые ответы не определяют имя проекта, target или выходные имена.

Локальные `AGENTS.md` и `00_README.md` хранятся отдельно от пользовательского списка файлов и передаются только для выбранного проекта. Полный ZIP проекта сохраняет их вместе со спецификацией, C, скрытым YAML, описаниями и изображениями. Текст локальных правил, включая UTF-8 BOM и CRLF, не переписывается.

Язык непомеченного описания определяется по содержимому, когда его можно распознать. `und` означает неизвестный язык, а не английский и не явный выбор пользователя: агент определяет язык самого существующего описания либо запрашивает уточнение. Если существуют отдельные описание по умолчанию и вариант на том же языке, они сохраняются раздельно; служебный ключ вида `ru-x-default` различает варианты и сохраняет русский базовый язык. Пустая заготовка описания заменяется при первой генерации, даже если фактический язык отличается от её первоначальной метки.

- Таблица стадий используется как общий источник допустимых действий и выходных ролей.
- Предварительные проверки возвращают конкретное уточнение до платного вызова, когда препятствие можно определить локально: идентичность проекта, текущий C, неоднозначный или неподдерживаемый target, имена выходов, повреждённые маркеры и указания в защищённых областях.
- Проверка результата контролирует область стадии, неизменность спецификации и пользовательского кода, структуру C/YAML и локализацию замечаний. Компиляция выполняется сервером отдельно.
- Успешная компиляция не означает проверку на аппаратуре. Сохранённая ревизия источника не объявляется самой свежей в сети без отдельной проверки.
- Автотесты общей политики проверяют таблицу стадий, её неизменность, соответствие транспортной схеме и сообщения английского/русского предварительного ответа. Поведенческие проверки интеграции должны покрывать все стадии, разрешения, маркеры, языки, имена и неоднозначные входы.

Новые материалы репозитория по-прежнему попадают на сервер в исходном виде. Изменения его правил нужно проверять против общей политики и контрактных тестов, сохраняя единое место адаптации вместо новых независимых исключений в промпте.

## Повторяемая проверка через модель

`npm run eval:project-policy --prefix backend` — отдельная платная проверка, которая запускается только явно с `AI_ENABLED=1`, настроенным ключом OpenAI, `AI_MATERIALS_ROOT` и доступным компилятором. Обычный CI её не запускает. Модель берётся из действующей конфигурации; проверенный вариант — `gpt-6.1-sol`.

Она проверяет полный цикл: Review готовой спецификации с посторонним примером внутри code fence и локальным `AGENTS.md`; вопросы на пустом русском черновике; генерацию рабочего C/YAML и реальную компиляцию; русское описание фактического C после вставки пользовательской переменной. Каждый запрос к модели проверяется на наличие всех четырёх полных исходных документов ровно один раз перед общей политикой. Исходные правила и секреты не выводятся в журнал.

`PROJECT_POLICY_EVAL_OUTPUT` задаёт отдельную папку для результатов проверки; `PROJECT_POLICY_EVAL_CASES` позволяет выбрать нужные сценарии (`review,empty-ru,generate,describe`). Для отдельного `describe` нужен ранее сохранённый результат `generate`. Аппаратная проверка этой процедурой не выполняется.
